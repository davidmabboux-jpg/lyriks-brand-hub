Le concept

C'est quoi Lyriks, en une phrase ?
Dans un monde où les équipes qui designent et codent avec l'IA en ont assez de dépenser des fortunes en tokens et de subir des hallucinations, Lyriks est la couche de cohérence qui permet de briefer parfaitement les IA.
C'est quoi le problème que vous résolvez, concrètement ?
L'IA transforme l'ambiguïté en code plus vite que les équipes ne se mettent d'accord. Résultat : entre ce que le PM a en tête, ce que le designer dessine et ce que l'IA génère, on obtient trois produits différents. Ça crée des reprises, des bugs découverts tard, et une dérive entre l'intention et l'implémentation. On supprime cette dérive.
C'est quoi Lyriks Community (l'open source) ?
Lyriks Community est la couche open source (AGPL, local-first), le moteur, celui que les devs installent. Lyriks (enterprise) est la plateforme au-dessus : collaboration, gestion des droits, supervision des usages IA, déploiement managé. En résumé : Lyriks Community = le moteur open source ; Lyriks = la plateforme construite par-dessus.Si on vous parle d'« Unspaghettit » : c'est l'ancien nom de notre licence open source, aujourd'hui Lyriks Community.
Ce n'est pas juste un énième outil de doc produit ?
Non, et c'est la distinction clé. Un outil de doc stocke de l'information. Nous, on vérifie la cohérence : on détecte les contradictions entre intention, design et code, on simule les comportements avant le build, et on compare l'implémentation à la spec. Et surtout, c'est lisible et exploitable par les agents IA.
2

Comment ça marche

Concrètement, qu'est-ce qu'on manipule ?
On modélise le comportement du produit en entités structurées : fonctionnalités, interactions utilisateurs, actions, états, règles, effets, data. Au lieu de prose qui périme, on a une spécification structurée que les humains et les agents peuvent inspecter, simuler, éditer et auditer.
C'est quoi cette histoire de "spec exécutable" ?
La spec n'est pas de la documentation passive : les scénarios qu'on définit deviennent des tests, passés dans un simulateur avant qu'une ligne de code n'existe. Elle devient un contrat qui casse bruyamment quand quelque chose cloche, au lieu d'un wiki qu'on oublie de mettre à jour.
Après le développement, comment vous savez si le code respecte la spec ?
Un index relie chaque entité de la spec à un emplacement précis dans le code (fichier, ligne, signature). Le système réconcilie spec et code dans les deux sens : ce qui est spécifié mais pas implémenté, et ce qui est implémenté mais hors-spec. On voit la couverture, les écarts et les potentielles régressions.
Ça remplace les tests unitaires ?
Non, ça intervient en amont. Les tests unitaires vérifient que le code fait ce que le code dit. Nous, on vérifie que l'intention est cohérente avant le code, et que le code livré correspond à l'intention. C'est complémentaire, pas concurrent.
Qui écrit la spec, le PM, le dev, ou l'IA ?
Les trois peuvent y contribuer, et c'est l'intérêt : c'est une définition partagée. Le PM y porte l'intention et les règles métier, le designer les parcours, le dev la dimension technique, et l'agent IA peut aussi proposer et éditer via l'interface dédiée. Ça vaut aussi pour le solo builder, ces profils multi-expertise qui mènent un produit seuls de bout en bout : la spec leur tient lieu de fil conducteur partagé avec leurs agents.

Intégration & IA

Ça marche avec quels outils de code IA ?
Avec tous les agents qui parlent le protocole MCP : Claude Code, Cursor, Codex, et les environnements compatibles. L'agent lit la spec via MCP au lieu de deviner le contexte dans un prompt à rallonge.
C'est quoi MCP, pour ceux qui ne connaissent pas ?
Le Model Context Protocol : un standard qui permet à un agent IA d'accéder à des outils et des sources de contexte de façon structurée. Concrètement, notre serveur expose la spec à l'agent par appels typés, il peut l'inspecter, la simuler, l'éditer, l'auditer.
En quoi ça améliore ce que produit l'IA ?
L'agent code à partir d'une définition vérifiée plutôt que d'une interprétation. Moins d'hallucinations (il ne réinvente pas des règles), moins d'oublis (il voit les états et exceptions), et il code la bonne version du premier coup au lieu d'être re-prompté quinze fois. En résumé : le 1er prompt est le bon prompt.
Il faut changer notre façon de travailler avec l'IA ?
Non, on se branche sur les agents que vous utilisez déjà. On ajoute une couche de contexte structuré ; on ne remplace pas votre IDE ni votre agent.
Ça gère quels langages / frameworks ?
La spec décrit le comportement du produit, pas un langage particulier, elle est agnostique. L'audit code-vers-spec s'appuie sur l'indexation de votre base.Précisions techniques selon votre stack à donner par le Démonstrateur.

Comparaisons

Quelle différence avec Notion / Confluence / un wiki ?
Ces outils stockent de la connaissance, mais ne vérifient rien. Le problème n'est pas le manque de doc, c'est qu'aucun de ces outils ne détecte une contradiction entre l'intention, le design et le code, ni ne se relit par une IA de façon structurée. Nous, c'est exactement ça notre métier.
Quelle différence avec Jira / un outil de tickets ?
Jira suit l'avancement du travail. Nous, on garantit la cohérence de ce qui est défini et livré. Un ticket peut être « done » alors que l'implémentation a dérivé de l'intention, c'est ce trou qu'on couvre.
Copilot / Cursor ont déjà du contexte sur mon repo. Pourquoi vous ?
Leur contexte, c'est votre code existant, ce qui a déjà été écrit, avec ses éventuelles erreurs. Nous, on apporte l'intention vérifiée : ce que le produit doit faire. L'agent ne se contente plus de prolonger l'existant, il code contre une définition correcte.
C'est pas un truc que GitHub ou Cursor vont intégrer demain ?
Côté produit : notre valeur est dans le formalisme de modélisation du comportement et le moteur de vérification, pas dans une simple fonctionnalité d'éditeur. Ce formalisme s'appuie sur 10 ans de recherche sur la théorie des graphes, un partenariat avec le CNRS et un brevet en cours de dépôt : ça ne se réplique pas en une feature.→ Angle moat / défensibilité : voir la FAQ business

Open source & déploiement

C'est open source ? Sous quelle licence ?
La couche Lyriks Community est open source sous licence AGPL-3.0. L'édition Community est libre pour un usage non commercial.
Quels sont les niveaux de déploiement ?
Trois : Community (open source, local-first, usage non commercial), Enterprise self-service (déploiement autonome), et Enterprise managé (hébergé et accompagné par nos soins). Les fonctions de collaboration avancée, gestion des droits et supervision relèvent de l'enterprise.
On peut l'héberger chez nous (self-host) ?
Oui. L'approche est local-first et le self-hosting fait partie du modèle. Vos données restent dans votre environnement.
C'est construit avec quoi ?
Côté technique : SvelteKit et TypeScript, avec un dashboard, un mode hub multi-repos, de la collaboration temps réel, et de l'export chiffré.Le Démonstrateur peut entrer dans le détail si un dev creuse.

Sécurité & données

Où vont nos données ? C'est dans le cloud ?
L'approche est local-first : par défaut, la spec et le contexte restent dans votre environnement. C'est un argument fort pour les équipes sensibles à la confidentialité de leur code et de leur roadmap. Et quand on passe par le cloud, vos données sont hébergées en France chez OVH ; on fait d'ailleurs partie de l'OVH Startup Program.
Notre code source part chez vous ?
Non, le principe local-first est précisément là pour éviter ça.⚠ Détails contractuels / garanties enterprise → échange dédié, ne pas improviser d'engagement sécurité sur le stand
C'est conforme RGPD ?
Oui, totalement conforme au RGPD, ainsi qu'à ses équivalents pour les États-Unis (CCPA) et pour l'Asie (PDPA).⚠ Confirmer les intitulés exacts avec l'équipe légale ; pour le détail contractuel, orienter vers un échange dédié.

Pour démarrer

Comment on teste, concrètement ?
Pour la couche open source (Lyriks Community) : une installation en ligne de commande, branchée sur l'IDE en quelques minutes. Scanne le QR du stand pour accéder au repo.
Combien de temps pour voir un résultat ?
L'idée est justement un time-to-value court : on installe, on modélise une première fonctionnalité, on lance la vérification, et on voit immédiatement les écarts de cohérence. C'est ce qu'on montre en démo en 3 minutes. Et en moins de 2 à 3 heures, vous pouvez créer un produit from scratch 100 % cohérent.
Vous accompagnez la mise en place ?
Oui, sur les profils chauds, on propose un créneau de 20-30 minutes en visio pour aider à câbler l'outil sur un vrai projet. C'est aussi une porte d'entrée pour les design partners.
Où je trouve plus d'infos ?
Sur le site lyriks.io pour la vision et les cas d'usage, et le repo GitHub (open source) pour le concret technique. Pour un échange approfondi : on cale une démo de 45 minutes sur votre produit.
